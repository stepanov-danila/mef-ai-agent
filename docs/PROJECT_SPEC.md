# MEF AI Copilot — Общая спецификация проекта

Версия документа: 1.0

---

## 1. Назначение системы

MEF AI Copilot — это интеллектуальный ассистент для ML-инженеров, который автоматизирует создание, валидацию и объяснение конфигураций для платформы MEF (ML Execution Framework).

---

## 2. Бизнес-задача

ML-инженерам при деплое моделей в MEF требуется заполнять сложный JSON/YAML-конфиг (`mef-config.json`), содержащий сотни полей со строгими форматами, зависимостями от Vault (секреты), OpenShift, Istio и других компонентов инфраструктуры.

Ключевые проблемы:

- Высокий порог входа — нужно знать сотни параметров
- Ошибки выявляются только после запуска пайплайна (долгий цикл)
- Риск утечки секретов при ручном копировании
- Сложность миграции при обновлении версии платформы

Цель Copilot — снизить порог входа, ускорить деплой и исключить человеческие ошибки через AI-ассистента, который понимает структуру конфига и помогает инженеру на всех этапах.

---

## 3. Пользователи

| Роль | Потребности |
|---|---|
| ML-инженер | Быстро создать валидный конфиг, понять формат полей, исправить ошибки |
| DevOps / Platform Engineer | Проверить конфиги перед деплоем, обучить новых сотрудников |
| Team Lead | Стандартизировать конфигурации, ускорить релизный цикл |

---

## 4. Функциональные требования

### 4.1 Генерация конфигураций

- Создание минимального валидного шаблона по запросу
- Генерация конфига под конкретный тип модели (PythonModel, JavaModel, SparkApplication, Triton и др.)
- Автозаполнение обязательных полей плейсхолдерами
- Подстановка имени модели, указанного пользователем

### 4.2 Валидация и исправление

- Проверка готового конфига по актуальной JSON Schema
- Возврат списка ошибок с указанием конкретных полей и причин
- Предложение конкретных исправлений с объяснением
- Автоматическая коррекция простых ошибок (формат, тип данных)

### 4.3 Обучение и документация

- Объяснение назначения любого поля в конфиге
- Демонстрация формата (regex, enum, примеры)
- Подсказки по типичным сценариям использования
- Ссылки на внутреннюю документацию (в перспективе)

### 4.4 Чат-интерфейс

- Диалог с AI-агентом на естественном языке (русский)
- Поддержка контекста диалога (сессия)
- Вывод результатов в читаемом формате с подсветкой кода
- Возможность загружать свой конфиг для проверки

## 5. Технические требования

### 5.1 Backend

- Node.js (TypeScript)
- REST API (Express)
- Интеграция с GigaChat (LLM через корпоративный HTTPS с mTLS)
- JSON Schema Draft-04 парсер с резолвингом `$ref`
- Агентная архитектура с циклом выполнения инструментов

### 5.2 Frontend

- Vite + React + TypeScript
- Monaco Editor (подсветка JSON/YAML)
- UI для чата
- Визуализация ошибок валидации прямо в редакторе

### 5.3 Инструменты агента

| Инструмент | Назначение |
|---|---|
| `validate_mef_config` | Валидирует конфиг против JSON Schema |
| `get_schema_info` | Возвращает метаданные поля (тип, обязательность, паттерн) |
| `generate_config_template` | Создаёт минимальный валидный шаблон |

### 5.4 Безопасность

- Маскировка чувствительных данных (пароли, токены, keySet)
- Запрет на запрос реальных секретов через системный промпт
- mTLS для работы в корпоративной сети
- Ограничение скорости запросов (rate limiting)

### 5.5 Производительность и масштабирование

- Кэширование схемы в памяти
- InMemory-сессии с TTL 30 минут
- Возможность перехода на Redis в будущем
- Асинхронная обработка запросов

## 7. Ограничения и допущения

### 7.1 Текущие ограничения

- Работа только с JSON-форматом (не YAML)
- `oneOf`/`anyOf` валидируются по стандартной семантике JSON Schema
  (конфиг валиден при совпадении с любой подходящей веткой); неявные
  объединения через `minProperties`/`maxProperties` (например, «ровно
  одно из двух полей») по-прежнему валидируются как обычные ограничения,
  но не распознаются как объединения для целей атрибуции ошибок
- Нет поддержки межполевой валидации (зависимости полей)
- Сессии только в памяти (перезапуск сервера сбрасывает историю)

### 7.2 Допущения

- Схема соответствует Draft-04 (не меняется версия JSON Schema)
- Пользователи имеют доступ к корпоративной сети
- GigaChat доступен через корпоративный шлюз

## 9. Ключевые принципы архитектуры

1. Нет хардкода — вся информация о полях извлекается из схемы.
2. Единый источник истины — только `mef-config.json`.
3. Агентный подход — LLM выбирает инструменты, бэкенд выполняет.
4. Безопасность прежде всего — секреты никогда не попадают в логи.
5. Готовность к изменениям — обновление схемы не требует переписывания кода.
